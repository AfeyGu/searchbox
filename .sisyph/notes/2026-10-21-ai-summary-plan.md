# AI 总结：调研与规划

日期：2026-10-21
状态：**方案讨论，未实施**

## 一、结论先行

建议做，而且比想象中便宜、比想象中简单——因为现有架构里已经有 80% 的零件。

**推荐形态**：结果页顶部一个「AI 总结」按钮，点击后把当前结果压成上下文交给模型，**流式**输出成一段带引用编号的摘要；引用编号可点，跳转到对应结果。**不做**自动总结、不做逐条摘要、不做多轮对话（首版）。

**推荐默认模型**：智谱 `GLM-4.x-Flash`（**免费**，128K 上下文，OpenAI 兼容协议）。DeepSeek 作为付费备选（约 **0.003 元/次**）。

---

## 二、需求边界

要解决：搜完之后不想逐条点开，希望先看到"这批结果说了什么"。

明确不做（首版）：

- 不做逐条结果的 AI 摘要（要抓正文、成本 ×N、慢）
- 不做多轮追问（留结构，不做 UI）
- 不做"自动对每次搜索都总结"（费用与限流不可控）
- 不做本地向量库/RAG（超出浏览器扩展的合理范围）

---

## 三、现状盘点：能直接复用什么

| 已有能力 | 对 AI 总结的意义 |
|---|---|
| **`fillValue` 整串占位符保留原始类型**（已实测，`fillValue("{{limit}}", {limit:10})` 返回数字 `10`） | 关键。`"messages": "{{messages}}"` 可以直接注入**消息数组**，不需要改替换引擎 |
| host 权限 + `origin` 数组 | 调用任何模型厂商的接口都能绕开 CORS，私有端点（如本地 Ollama）也能配 |
| `chrome.storage.local` 的 `keys` 结构 | API Key 存储、按配置隔离，已有现成机制 |
| 请求执行器 `runSource` | 超时、权限预检、错误归类都现成 |
| 渐进式渲染 + 结果状态 | 可以判断"结果是否还在增长"，决定是否允许总结 |
| 来源标签 / 多来源记录 | 引用编号可以映射回具体 URL，这是通用聊天界面做不到的 |

**结论**：AI 总结不是"新子系统"，而是"给现有解释器加一种输出形态"。

---

## 四、交互形态对比

| 形态 | 触发 | 成本 | 延迟感知 | 复杂度 | 评价 |
|---|---|---|---|---|---|
| **A. 点击总结（推荐）** | 用户点按钮 | 每次 1 次调用 | 流式首字 1–2 秒 | 低 | 不点不花钱；用户有明确预期 |
| B. 自动总结 | 每次搜索后 | 每次搜索 1 次 | 无需操作，但要等结果收敛 | 中 | 免费模型限流会被打爆；费用不可控 |
| C. 逐条 AI 摘要 | 每条结果旁 | N 次调用 + N 次抓正文 | 每条都要等 | 高 | 首版不做 |
| D. 多轮追问 | 总结后继续问 | 累计上下文 | 交互更复杂 | 中高 | 结构上预留，首版不做 |

**推荐 A**，并把 B 做成设置里的可选开关（默认关），等 A 稳定后再开。

## 五、模型接入调研（全部在真实扩展环境实测）

用无效 key 打了一次，只验证**可达性**与错误格式（不消耗任何额度）：

| 厂商 | 端点 | 实测 | 计费 | 备注 |
|---|---|---|---|---|
| **智谱** | `https://open.bigmodel.cn/api/paas/v4/chat/completions` | **401**（184 ms） | **GLM-4.7-Flash / 4.5-Flash 免费**，128K 上下文 | 首选。免费但有并发/频率限制 |
| **DeepSeek** | `https://api.deepseek.com/chat/completions` | **401**（416 ms） | 输入 1 元/百万（空闲）、输出 4 元/百万 | 便宜、稳定、中文好 |
| **OpenAI** | `https://api.openai.com/v1/chat/completions` | **401**（780 ms） | 显著更贵 | 网络可达，作为可选 |
| **Ollama 本地** | `http://localhost:11434/v1/chat/completions` | 连接被拒（未安装，2 ms） | 免费 | 隐私最优；需额外权限 `http://localhost/*` |

三家云厂商都返回了标准 JSON 错误（而不是跨域报错），说明**扩展可以直接调用，不存在 CORS 障碍**。

## 六、成本测算

单次总结的上下文：10 条结果 ×（标题约 30 字 + 摘要约 120 字）≈ 1500 字，加系统提示约 200 tokens，**输入约 1400 tokens**；输出约 300 tokens。

| 模型 | 单次成本 | 每天搜 30 次 | 每月 |
|---|---|---|---|
| GLM-4.7-Flash | **0 元**（限流） | 0 元 | 0 元 |
| DeepSeek（空闲时段） | 1400×1 + 300×4 = 0.0026 元 | 0.078 元 | ≈ **2.3 元** |
| DeepSeek（高峰） | 0.0052 元 | 0.156 元 | ≈ 4.7 元 |

**结论：钱不是约束，限流才是。** 免费模型的价值在于把"要不要做"变成纯技术问题。

## 七、技术设计

### 7.1 配置放在哪

不建议塞进现有的"搜索源"列表——搜索源是"每次搜索都跑的一条"，AI 是"手动触发、只有一个在生效"。语义不同，混在一起会让 UI 和逻辑都变形。

建议：设置页新增「**AI 总结**」区块，存一个独立配置对象；但**请求/响应结构复用同一套解释器**。

```jsonc
{
  "enabled": true,
  "id": "glm-flash",
  "name": "GLM-4.7-Flash",
  "origin": "https://open.bigmodel.cn",
  "request": {
    "url": "https://open.bigmodel.cn/api/paas/v4/chat/completions",
    "method": "POST",
    "headers": { "Authorization": "Bearer {{key}}" },
    "body": {
      "model": "glm-4.7-flash",
      "messages": "{{messages}}",     // 整个数组注入，复用现有整串占位逻辑
      "stream": true,
      "temperature": 0.3
    }
  },
  "response": {
    "stream": true,                    // true=按 SSE 增量读取；false=一次性取文本
    "textPath": "choices.0.message.content"
  },
  "prompt": {
    "system": "你是搜索助手。只依据给出的结果作答，不确定就说不确定。用中文，200 字以内，需要时用 [1][2] 标注来源编号。",
    "detail": 10                       // 取前几条结果，默认 10
  }
}
```

### 7.2 引擎要新增的东西（按侵入性排序）

| 改动 | 位置 | 量级 |
|---|---|---|
| 构造 `messages` 数组 | 新模块 `core/ai.js` | ~40 行 |
| SSE 流式读取（`response.body.getReader()` 解析 `data:` 行） | `core/request.js` 新增 `runStream` | ~50 行 |
| 设置页 AI 区块（模型配置 + Key + 测试按钮） | `options.*` | ~120 行 |
| 结果页总结卡片（按钮、流式渲染、引用映射） | `search.*` | ~150 行 |
| 自检新增断言 | `tests.js` | ~40 行 |

总计约 **400 行**，不触碰现有的搜索结果链路——**AI 失败不影响搜结果**。

### 7.3 Prompt 与上下文构造

```
system: 你是搜索助手。只依据给出的结果作答……
user:   用户查询：{query}

        以下是搜索结果：
        [1] 创建您的第一个应用程序 — electronjs.org
            学习目标：在本节，您会学习如何创建您的 Electron 项目……
        [2] Electron 教程 | 菜鸟教程 — runoob.com
            ……
```

约束：每条摘要截断到 200 字，总条数受 `prompt.detail` 控制，保证输入稳定在 ~1500 tokens。

### 7.4 引用映射（我们的独特优势）

模型返回 `[1][2]` → 渲染时替换为 `<a href="第1条结果的url">[1]</a>`。
点击即在当前页或新标签打开对应结果——通用聊天界面做不到这点。

渲染只需极简 Markdown：段落、列表、`**加粗**`、`[n]` 引用。不引入第三方库。

### 7.5 流式输出

- `stream: true` → 逐块追加文本，用户 1–2 秒看到首字
- 若用户配的端点不支持流式（返回普通 JSON）→ 自动回退非流式
- 中断：切换查询/关闭卡片时 `AbortController.abort()`

### 7.6 错误与边界

| 情况 | 处理 |
|---|---|
| 未配置 AI / 未填 Key | 按钮禁用，提示"去设置页配置" |
| 429 限流 | 卡片内提示"该模型限流，稍后再试"，不影响搜索 |
| 结果还在返回中 | 按钮可用但标注"还有 N 个来源搜索中，总结可能不全" |
| 模型输出为空 | 提示重试，记录原始响应到测试面板 |
| 网络/权限错误 | 复用现有错误文案体系 |

## 八、里程碑

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| **M1** | AI 配置 + 非流式总结 + 卡片 + 引用 | 点按钮 3 秒内出摘要；引用编号可点且跳对；自检新增断言全绿 |
| **M2** | 流式输出 | 首字 ≤ 2 秒；中途可取消；失败自动回退非流式 |
| **M3** | 自动总结开关（默认关）+ 重新总结 | 开关关闭时零调用（可用请求计数验证） |
| **M4** | 本地 Ollama 示例配置 | 无 key 也能跑通，验证隐私路径 |

## 九、风险

| 风险 | 影响 | 对策 |
|---|---|---|
| **幻觉** | 摘要编造不存在的内容 | 强约束 prompt + 强制引用 + 显示"基于 N 条结果" |
| **隐私** | 查询和结果被发给第三方 | 首次使用明确提示；提供本地 Ollama 路径；默认不开启 |
| **限流** | 免费模型 429 | 非阻塞提示；手动触发而非自动；M3 才考虑自动 |
| **能力差异** | 小模型总结质量参差 | 可换模型；配置里可调 temperature/detail |
| **配置复杂度** | 比搜索源更难写 | 内置一份可直接用的默认配置（填 key 即用），高级用户再改 |

## 十、需要你决策的 5 件事

1. **触发方式**：只做"点击总结"，还是同时做"自动总结"开关？
2. **首版要不要流式**？流式体验好，但要多写约 50 行 + 处理中断逻辑；不做的话 M1 可以更快落地。
3. **要不要内置一份默认 AI 配置**（智谱 GLM-Flash，填 key 就能用）？这跟"内置搜索源保持通用"的原则不冲突，但会引入一个厂商名。
4. **摘要范围**：只用当前视图（可能是单源过滤后），还是始终用"全部"的合并结果？
5. **是否允许自定义 prompt 模板**？允许的话灵活，但用户写坏了难排查；也可以只暴露"详略程度"这样的旋钮。
