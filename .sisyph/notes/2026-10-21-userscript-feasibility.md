# 移植成油猴脚本（Tampermonkey）可行吗

日期：2026-10-21
状态：**可行性调研，未实施**

## 一、结论

**技术上可行，但会丢掉三样东西，并且要改变产品形态。**

核心逻辑（配置解释器、合并去重、历史、AI 总结的请求构造）约 **70% 可直接复用**；丢掉的是"扩展"提供的三样平台能力：新标签页接管、原生划词右键菜单、内置站点图标。流式输出有替代方案，但依赖较新的 Tampermonkey 版本。

**建议**：如果你只是自己用，现有扩展已经更好；油猴版真正的价值是**分发**——别人不用装扩展、点一下就能用。

---

## 二、实测证据（决定可行性的两个事实）

### 1. 纯网页方案不可行

AnySearch 接口的响应头里**没有任何 CORS 放行头**：

```
HTTP/1.1 200 OK
content-type: application/json
x-ratelimit-limit: 10
server: envoy
（无 access-control-allow-origin）
```

意思是：从普通网页（含 GitHub Pages 上的静态页面）直接 `fetch` 会被浏览器拦掉。所以要么是扩展、要么是油猴——**必须有能绕开 CORS 的通道**。油猴这边的通道是 `GM_xmlhttpRequest`。

### 2. 流式输出可以做，但有条件

Tampermonkey 文档里 `GM_xmlhttpRequest` 支持：

- `responseType: 'stream'`，`onloadstart` 里能拿到 stream 对象
- `onprogress` 会**分块**给出 `responseText`（文档标注 v5.6.6242+ 起）

所以 SSE 流式可以保留，但要换一套 API 重写（我们目前用的是 `fetch` + `response.body.getReader()`）。
注意文档明确写的两个副作用：设成 `stream` 后 `details.timeout` 不生效、`onreadystatechange` 只会收到一次 DONE。

## 三、能一一对应上的能力

| 扩展里的能力 | 油猴里的等价物 | 备注 |
|---|---|---|
| `chrome.storage.local` | `GM_setValue` / `GM_getValue` | 换成同步 API，包一层 Promise 即可 |
| `host_permissions` + fetch | `GM_xmlhttpRequest` + `@connect` | **绕过 CORS**，能力等价 |
| `chrome.tabs.create` | `GM_openInTab` / `window.open` | 等价 |
| 页面 UI（HTML/CSS/JS） | 直接注入 DOM | 等价 |
| 键盘交互（↑↓/Enter/Esc） | 原生事件 | 等价 |
| 权限按域名逐一申请 | `@connect` 声明 + 首次访问弹窗 | 用户体感相似 |
| 纯函数核心（解析/合并/历史/AI） | 原样复用 | **约 70% 代码** |

## 四、迁移不了的三样（硬伤）

### 1. 新标签页接管 —— 做不到

扩展靠 `chrome_url_overrides` 把新标签页换成自己的页面。油猴运行在**别人网页的上下文里**，没有"自己的页面"这个概念，也无法接管 `chrome://newtab`。

替代形态只有两条：

- **A. 宿主页面型**：把搜索页放到 GitHub Pages（例如 `https://afeygu.github.io/searchbox/app.html`），脚本 `@match` 这个地址，把它变成完整的搜索页。可以加书签、可以设成浏览器主页。
- **B. 任意页面浮层型**：脚本在所有页面生效，按快捷键（如 `Ctrl+K`）弹出搜索浮层，`Esc` 关闭。

### 2. 原生划词右键菜单 —— 只能变通

扩展能注册 `contextMenus`，菜单项只在有选区时出现。油猴的 `GM_registerMenuCommand` 只是往油猴菜单里加一条，做不到"选中文字才出现"。

变通方案：监听 `mouseup`，检测到有选区就浮出一个小按钮「用 Searchbox 搜索」。**体感接近，但不是原生菜单**，也要处理"误触发"（比如拖拽选中、双击选词）。

### 3. 站点图标 —— 拿不到了

扩展用的是 `chrome://favicon/?pageUrl=...`，这是 Chrome 给扩展的私有接口，网页里加载 `chrome://` 会被拒。

替代：用第三方 favicon 服务（Google s2 / DuckDuckGo）——**但这意味着把每条结果的域名发给第三方**，与"低依赖"的设计取向冲突。更干净的做法是去掉图标，用首字母色块。

## 五、还有一个工程量不大但绕不开的问题

油猴脚本是**单文件**，而我们现在的代码是 6 个 ES 模块互相 `import`。要迁移必须先加一个打包步骤：

- 方案一：引入 `esbuild`（一条命令打包，最省事）
- 方案二：手写拼接脚本（我们是零依赖项目，但拼接要处理 import 顺序，脆）

另外 `core/` 里对 `chrome.storage` 的调用要替换成 `GM_*`，大约 30 行适配层。

## 七、工作量估算

| 项 | 量级 |
|---|---|
| 存储适配层（`chrome.storage` → `GM_*`） | 30 行 |
| 请求层（`fetch` → `GM_xmlhttpRequest`，含流式） | 80 行，**且要重测流式** |
| 打包脚本 | 40 行 |
| 宿主页 / 浮层 UI | 150 行（改造现有 UI） |
| 划词浮标 | 60 行 |
| 图标方案 | 20 行 |
| **合计** | **约 380 行新代码 + 一轮完整回归** |

时间上和当初做 AI 总结差不多，但**风险更高**：流式依赖油猴版本，且无法用现在的测试方式验证（自检页能跑，但 `GM_*` API 只能在真实油猴环境里测）。

## 八、建议

1. **如果你要的是"自己用得更爽"** → 继续用扩展，油猴版没有收益，反而丢功能。
2. **如果你要的是"发给别人用"** → 油猴版价值很大（不用开发者模式、跨浏览器），建议选 **形态 A（宿主页）**：体验最接近现在的产品，也是唯一能"打开就有搜索页"的方案。
3. 折中路线：保留扩展为主，另出一个**精简油猴版**（只做宿主页 + 搜索 + 合并去重 + AI 总结，不做划词浮标），工作量能压到 250 行左右。
